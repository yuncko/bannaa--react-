# بنّاء (Bannaa) 🏗️ — Lovable-Style React Generator

أداة ذكاء اصطناعي تحوّل وصفك النصي إلى **مشروع React + TypeScript كامل ومتعدد المكوّنات** يعمل فورًا — تمامًا مثل منصات **Lovable.dev** و **v0.dev** — مبنية بـ Next.js 16 ومدعومة بنموذج **Gemini 2.5/3.5 Flash**.

---

## ✨ المميزات الرئيسية

1. ⚛️ **مشاريع React حقيقية ومعيارية**:
   - لا مزيد من صفحات HTML البسيطة! يُنتج التطبيق هيكلية مشروع متكاملة:
     - `src/App.tsx`: المكوّن الرئيسي وتجميع الحالة
     - `src/components/Navbar.tsx`: شريط التنقل المتجاوب
     - `src/components/Hero.tsx`: قسم الواجهة الرئيسية
     - `src/components/Features.tsx`: المزايا والبطاقات
     - `src/components/Pricing.tsx`: جداول الأسعار
     - `src/types.ts`: أنواع TypeScript ونماذج البيانات
2. 👁️ **معاينة حيّة فورية داخل المتصفح**:
   - مُجمّع (Bundler) ومحلل وحدات في الذاكرة يقوم بترجمة TypeScript وJSX عبر Babel Standalone وتشغيل React وTailwind CSS وLucide Icons فورًا في المتصفح دون الحاجة لخادم بناء خارجي.
3. 💻 **مستعرض كود تفاعلي شبيه بـ Lovable**:
   - شجرة ملفات تفاعلية (File Explorer)
   - تبويبات للملفات المفتوحة (Tabs)
   - تلوين برمجي متطور لكود TSX/CSS/JSON
   - أزرار نسخ لكل ملف أو لكامل المشروع
4. 📱 **التحكم بأحجام العرض المتجاوبة**:
   - سطح المكتب (Desktop 100%)
   - أجهزة لوحية (Tablet 768px)
   - هواتف ذكية (Mobile 375px)
5. 📦 **تصدير كود المشروع بضغطة زر كـ Vite + React ZIP**:
   - يمكنك تنزيل ملف `.zip` يحتوي على مشروع Vite + React + TypeScript + Tailwind جاهز تمامًا للتشغيل محليًا عبر:
     ```bash
     npm install
     npm run dev
     ```
6. 🔄 **تعديلات وتكرارات ذكية**:
   - يمكنك الاستمرار في تحسين وتعديل التطبيق عبر المحادثة (مثل: "أضف وضع ليلي"، "أضف زر فلترة"، "غيّر الألوان إلى الزمردي").
7. 🎁 **رصيد ترحيبي 5$ لكل حساب جديد**:
   - يُمنح مرة واحدة لكل صندوق بريد Gmail حقيقي، ويظهر في نافذة ترحيب عند أول دخول.
   - الرصيد معروض دائمًا في رأس الصفحة وفي `/account`، ويتحوّل إلى ختم `SOLD OUT` عند النفاد.
   - سعر كل رسالة ظاهر قبل إرسالها بجوار مُنتقي النموذج — عدّاد لا يُخفي نفسه.

## 🚀 التشغيل محليًا

1. تثبيت الحزم:
```bash
npm install
```

2. أنشئ ملف `.env.local` (انسخه من `.env.example`) وضع فيه مفاتيح Omnirouter:
```env
OMNIROUTER_API_KEY_1=your_first_key
OMNIROUTER_API_KEY_2=your_second_key
OMNIROUTER_API_KEY_3=your_third_key
```
> المفاتيح تُقرأ من متغيّرات البيئة على الخادم فقط، ولا تُضمَّن في كود المتصفح.
> ملف `.env.local` مستثنى من Git ولا يجب رفعه أبدًا.

3. تشغيل خادم التطوير:
```bash
npm run dev
```

4. افتح [http://localhost:3000](http://localhost:3000) في المتصفح.

## 🔐 تسجيل الدخول (Supabase)

تسجيل الدخول **اختياري**: بدون متغيّرات Supabase يعمل التوليد كما هو، وتظهر شاشات
الدخول برسالة توضّح المتغيّر الناقص بدلًا من أن تتعطّل.

### 1. المتغيّرات

أضف إلى `.env.local`:

```env
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xxx
# مطلوب في الإنتاج فقط، لبناء روابط OAuth والبريد بعنوان الموقع الصحيح
NEXT_PUBLIC_SITE_URL=https://your-domain.com
```

المفتاح أعلاه **عام بطبيعته** — الحماية الفعلية للبيانات تأتي من Row Level
Security على الجداول. مفتاح `service_role` لا يُوضع في متغيّر `NEXT_PUBLIC_*`
ولا في كود العميل أبدًا.

### 2. إعدادات لوحة Supabase

في **Authentication → URL Configuration**:

- **Site URL**: `http://localhost:3000` للتطوير، وعنوان النشر في الإنتاج.
- **Redirect URLs** — أضف كل عنوان يُستخدم فعلًا:
  - `http://localhost:3000/auth/callback`
  - `http://localhost:3000/auth/confirm`
  - `https://your-domain.com/auth/callback`
  - `https://your-domain.com/auth/confirm`

عنوان غير مُسجَّل في هذه القائمة يُرفض، فيعود المستخدم إلى
`/login?error=exchange_failed`.

### 3. مزوّدو الدخول

في **Authentication → Sign In / Providers** فعّل:

| المزوّد | ما تحتاجه | عنوان العودة (Callback) في لوحة المزوّد |
| --- | --- | --- |
| Google | Client ID و Client Secret من Google Cloud Console | `https://<project-ref>.supabase.co/auth/v1/callback` |
| GitHub | Client ID و Client Secret من GitHub → Developer settings → OAuth Apps | `https://<project-ref>.supabase.co/auth/v1/callback` |

> عنوان العودة يُسجَّل عند Google/GitHub بعنوان **Supabase** لا بعنوان موقعك؛
> Supabase هي التي تعيد التوجيه بعدها إلى `/auth/callback` عندك.

مزوّد غير مُفعَّل يُنتج رسالة عربية واضحة («هذا المزوّد غير مُفعَّل على المشروع»)
بدل خطأ عام.

> **مطلوب:** المزوّدان مُعطَّلان افتراضيًا على مشروع جديد. حتى تفعّلهما، يعمل الدخول
> بالبريد فقط، وأزرار Google/GitHub تُرجع الرسالة أعلاه.

### 4. سياسة البريد: Gmail فقط

الرصيد الترحيبي يجعل صندوق بريد مؤقّتًا يساوي مالًا، فالتسجيل **مقصور على
Gmail** — وهو قرار منتج لا مرشِّح سبام: قائمة حجب النطاقات المؤقّتة معركة خاسرة،
وقائمة سماح بمزوّد واحد دقيقة.

القاعدة مطبَّقة في ثلاث طبقات، لأن أي طبقة وحدها قابلة للتجاوز:

| الطبقة | الملف | ما تمنعه |
| --- | --- | --- |
| النموذج | `lib/email-policy.ts` | رفض فوري قبل أي طلب شبكة |
| الخادم | `app/auth/actions.ts` | طلب مُرسَل يدويًا إلى الـ action |
| العودة من OAuth | `app/auth/callback/route.ts`، `app/auth/confirm/route.ts` | حساب Google بعنوان غير Gmail، أو رابط بريد لحساب قديم |

النطاق `googlemail.com` مقبول لأنه **نفس** صندوق Google باسم أقدم. وتُطبَّق القاعدة
على تسجيل الدخول أيضًا لا على الإنشاء فقط، كما طُلب: حساب أُنشئ قبل وجود القاعدة
يُمنع من الدخول برسالة تشرح السبب بدل «بيانات غير صحيحة».

Gmail يتجاهل النقاط في الاسم وكل ما يلي `+`، لذا يُجمَع كل بديل على بصمة واحدة
(`mailboxFingerprint` في TypeScript و`public.mailbox_fingerprint` في SQL) —
وبدونها يصنع صندوق واحد عددًا غير محدود من الحسابات وهدايا الـ 5$.

### 5. الرصيد والهدية الترحيبية (migration مطلوب)

من **Database → SQL Editor → New query** نفّذ ملف
[supabase/migrations/0001_credits.sql](supabase/migrations/0001_credits.sql)
مرة واحدة. ينشئ:

| العنصر | الوظيفة |
| --- | --- |
| `public.wallets` | صف لكل مستخدم: الرصيد بالسنت، الخطة، حالة الهدية |
| `public.credit_ledger` | سجل كل خصم وإيداع — هو مصدر الحقيقة للمراجعة |
| `public.welcome_grants` | بصمة كل صندوق بريد نال الهدية، بقيد فرادة |
| `provision_wallet()` | trigger على `auth.users` يُنشئ المحفظة عند التسجيل |
| `claim_welcome_grant()` | يمنح 5$ مرة واحدة لكل صندوق بريد حقيقي |
| `debit_credits()` | خصم ذرّي مع `reference` يجعل إعادة المحاولة لا تُحاسَب مرتين |
| `refund_credits()` | إرجاع خصم فشل عمله |

الأمان هنا أهم من الجدول: المشروع لا يحمل مفتاح `service_role` إطلاقًا، لذا
`wallets` و`credit_ledger` تمنحان `SELECT` على صفوفك فقط، **ولا** سياسة `INSERT`
أو `UPDATE` أو `DELETE` على الإطلاق. كل تعديل يمرّ عبر دالة `SECURITY DEFINER`
تستنتج المستخدم من `auth.uid()` ولا تأخذه كوسيط — فلا يستطيع متصل تسمية محفظة
غيره لأنه لا يوجد باراميتر لذلك. وكل دالة تضبط `search_path = ''` وتُسمّي كل كائن
بالكامل، وإلا أمكن اختطافها بكائن بنفس الاسم في مخطّط أسبق.

**قبل تنفيذ الـ migration** يظل التوليد يعمل: المحفظة غير المقروءة تُبلَّغ كـ
«غير متاحة» لا كخطأ، فإضافة الفواتير لا تُسقط الموقع حتى يُنفَّذ سكربت SQL يدويًا.

#### كيف يُحسب الاستهلاك

| النموذج | مشروع جديد | تعديل | إصلاح تلقائي |
| --- | --- | --- | --- |
| Claude Sonnet 5 | $0.45 | $0.25 | $0.12 |
| Claude Sonnet 4.6 | $0.30 | $0.18 | $0.09 |
| GPT-5.6 Luna / Terra | $0.25 | $0.15 | $0.08 |

الأرقام في `lib/billing.ts` وهي المصدر الوحيد الذي يتفق عليه الطرفان. وأهم ثلاث
قرارات فيها:

- **الخصم قبل العمل، والإرجاع عند الفشل.** المزوّد يحاسبنا على المحاولة، و«تحقّق
  ثم اخصم» يسمح لطلبين متزامنين بتجاوز فحص رصيد واحد.
- **النموذج المجهول يُحاسَب بأعلى سعر.** المسار يقبل `modelId` كما يأتي، فأي
  بديل أرخص من الأقوى يحوّل خطأ كتابة إلى خصم.
- **السعر يتبع النموذج الذي طلبه المستخدم**، لا الذي خدم الطلب بعد الـ failover.
  الـ failover مشكلتنا، وفاتورة تتغيّر لأن خيارنا الأول كان معطّلًا فاتورة لا
  يمكن توقّعها.

الإصلاح التلقائي **مخفَّض ولا مجاني**: العميل هو من يقرّر ما يُحسب إصلاحًا، فمسار
مجاني مسار قابل للتزوير. وأسوأ حالة لطلب فاشل = `create + 2 × repair`، وهي أقل من
الهدية الترحيبية بالكامل.

#### الخطط

| الخطة | السعر شهريًا | الرصيد الممنوح | الزيادة |
| --- | --- | --- | --- |
| Go | $14.99 | $18.00 | +20% |
| **Premium** (الأكثر شعبية) | $20.00 | $28.00 | +40% |
| Premium+ | $29.99 | $48.00 | +60% |

«الأكثر شعبية» ليست ملصقًا: Premium تحمل فعلًا أفضل رصيد لكل دولار من الطبقة
الأدنى، ويتحقّق `tests/billing.test.ts` من ذلك حتى لا يستطيع تغيير سعر أن يُخلّف
وعدًا قديمًا على الصفحة.

> ⚠️ **لا توجد بوابة دفع مربوطة.** `/pricing/checkout` يتوقّف عند صفحة تأكيد
> ويقول ذلك صراحة. هذا مقصود: البديل — زرّ يشحن المحفظة لأن أحدهم ضغطه — هو
> نقطة «مال مجاني» متاحة لأي صاحب حساب. لا يُمنح رصيد إلا عبر الهدية الترحيبية
> (مرة واحدة لكل صندوق بريد) حتى يشهد webhook من مزوّد دفع على عملية حقيقية.

### 6. قوالب البريد

هذا المشروع يتحقّق من الروابط على الخادم عبر `token_hash`، وهو الشكل الموصى به.
في **Authentication → Email Templates** اجعل الرابط في كل قالب:

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type={{ .Email.ActionType }}">
  تأكيد
</a>
```

القوالب الافتراضية التي تستخدم `{{ .ConfirmationURL }}` تعمل أيضًا: تصل إلى
`/auth/callback` بمعامل `code`، وهو مسار مدعوم كذلك.

### 7. المسارات

| المسار | الوظيفة |
| --- | --- |
| `/login` | دخول بالبريد أو عبر Google / GitHub |
| `/signup` | إنشاء حساب |
| `/forgot-password` | إرسال رابط إعادة التعيين |
| `/account` | بيانات الحساب، الرصيد، وختم `SOLD OUT` عند النفاد |
| `/account/password` | تعيين كلمة مرور جديدة |
| `/pricing` | الخطط الثلاث وجدول تكلفة كل نموذج |
| `/pricing/checkout` | ملخّص الخطة (بلا بوابة دفع، `noindex`) |
| `/auth/callback` | تبديل `code` بجلسة (PKCE / OAuth) |
| `/auth/confirm` | التحقّق من `token_hash` لروابط البريد |

`/account` و`/account/password` محميّان في `proxy.ts` وتُعاد التحقّق منهما داخل
الصفحة نفسها، فلا يكفي تعديل الـ matcher لتجاوزهما.
